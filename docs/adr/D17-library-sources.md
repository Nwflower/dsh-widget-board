# D17. 组件库的来源、提供方注册与数据源

## 背景

组件库原先只读包内的 `lib/widgets`：热重载监视的也是 `lib/`，发布之后它不再变化；用户与 agent 写的组件没有地方放，插件也没有路径提供自己的组件。同时，`loadLibrary` 遇到一个不合格的组件、或两个组件用了同一个 id，就整体抛出——一个坏目录让整个组件库起不来，看板也就打不开。卡片的数据只是一个静态字段，没有读数据的地方。

## 决定

- 组件库有三个来源，按传入顺序优先：`builtin`（包内 `lib/widgets`）、`user`（`$DSH_HOME/widget-board/widgets/`，启动时建出来）、`plugin`（插件经服务注册的目录）。
- 同一个 id 只认先到的来源，后到的记成一条错误；单个组件读不出来、manifest 不合格或 id 冲突，都只让这一个类型不可用，其余照常进库。用户与插件来源的目录不存在按空目录算；包内来源读不出来或一个组件都没有，直接抛出（构建没有写完）。
- 组件库的记录带上来源与提供方包名；界面按来源分组，读不出来的类型也列出来并写明原因。
- 出现过的每个版本存成 `$DSH_HOME/widget-board/blobs/<hash>.json`（来源、提供方与 base64 文件表），跨重启保留；内存只留最近用到的 32 份，其余从磁盘读，读回来先核对内容哈希。
- 宿主发布 cordis 服务 `widgetBoard`（`WIDGET_BOARD_API_VERSION = 1`）：`registerWidgetType`（目录，注册时读一次，目录不合格这一次注册抛出）、`registerDataSource`、`registerAction`。浏览器侧发布同名服务，`registerWidgetType` 收一个原生 React 组件，与宿主组件库里同 id 的组件对上（D3 的原生级）。每个注册返回释放函数，提供方卸载时随之撤下；提供方带来的版本与服务不一致时可见地拒绝（D12）。
- 原生组件收到的参数与 `window.widget` 同形（尺寸与位置、props、data、state、暂停状态、`setState`、`action`、`t`），一个组件从沙箱级换成原生级写法不必改；每个原生组件包一层错误边界，它抛错只废掉那一张卡。
- 卡片可以绑定一个数据源（`BoardInstance.source`）：组件可以在 manifest 里声明默认的数据源，加卡片时按它读第一次；`POST /instance/<id>/data` 可以再推一次；数据按组件的 `data` schema 校验，不符时拒绝写入并说明原因。组件的动作经 `POST /instance/<id>/action` 交给注册的动作，manifest 没声明的动作一律拒绝。
- 看板不再给组件库里的新组件自动补卡：新组件从题头的添加面板加入，卡片可以从卡片的移除按钮或组件不可用的占位里移除。第一次启动只给内置组件铺卡——装了插件不该顺带改变别人的看板。
- 卡片引用的组件不在组件库里不算启动错误：卡片保留盒子与状态，界面画成不可用的占位并写明原因，组件回来之后自动恢复。

## 后果

- 组件多了不会自己堆到看板上，要由用户或工具显式加入。
- 组件库的错误从「整库抛出」变成「逐个可见」，一个坏目录不再挡住启动，代价是界面要能显示不可用的条目。
- 数据源让卡片的数据来自插件而不是推送；推送与数据源是两条路径，组件的 `data` 是它们共同的落点。
- 版本跨重启保留之后，会话里内联显示过的组件与组件回退都有据可依；blobs 只增不减，清理要另做。

## 重审条件

- 出现两个以上真实的提供方之后，按它们实际的需要重新审视服务面的形状（D12 的重审条件同样适用）。
- 需要按来源做隔离（例如插件组件只允许出现在自己的看板里）时，重新决定来源表的优先级与命名空间。
- blobs 占用成为问题时，增加一个有引用的会话日志做依据的清理动作。
