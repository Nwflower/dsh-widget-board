# D18. 变更通知按事件推送

## 背景

变更通知原先只推一个修订号，页面收到就重取整份快照。番茄钟每秒写一次状态，开着的每个页面（包括正在写的那一个）都会因此每秒重取一次整份看板与组件库。卡片的状态、数据与布局都是小改动，快照却是整块看板。

## 决定

- SSE 每条消息是 `{ revision, event }`。事件有三种：`board`（卡片增删或组件库变化，页面重取快照）、`layout`（带整理后的布局与新的布局修订号）、`instance`（带这张卡的 `state`、对象补丁 `patch` 或 `data`）。
- 页面把 `layout` 与 `instance` 就地合并进手上的快照，只有 `board` 才重取；合并只认事件带来的字段，缺的字段保留原值。带 `patch` 时按一层合并，带 `state` 时整体替换（D23）。
- 接上连接时宿主先补一条 `board`，页面不必在「订阅」与「取快照」之间排先后；断线重连之后中间错过的改动由这条补齐。
- 浏览器半边把连续的状态补丁按窗口合并之后再提交（D23）；宿主每次收到仍然同步写入，没有延后写。
- 布局提交成功时，响应只带这次落定的盒子与修订号；修订号过期时回整份快照。页面把前者与布局事件按同一条规则合并。
- 拆除时长连接被结束：页面不会停在一条不再有消息的连接上。

## 后果

- 合并规则成了页面上的第二处业务逻辑，由单元测试盯着「只换带来的字段」。
- 两个页面同时改布局时，后到的提交仍收到 409 与当前快照，页面按宿主的那一份重画（D5、D16）。
- 状态事件带对象补丁时比整份状态小；单张卡的状态仍有额度，整份状态不会超过 64 KiB（D23）。
- 布局成功回包不再带全部看板的数据与状态，拖动一次的响应体只与改动的那几张卡有关。

## 重审条件

- 一张看板的快照大到重取一次也昂贵时（卡片上百、组件库很大），把 `board` 事件改成带增删的最小事件。
- 宿主提供插件级的实时通道（推送与鉴权都由宿主管）时，这一层改接宿主的通道。
