# D23. 状态写入的预算与合并

## 背景

沙箱组件的代码不可信（D3）。它每秒可以发 200 条消息，每条可以带 16KB 的状态补丁；宿主每收一条都要把整块看板写进磁盘（D5），事件还要把改动推给每个在线页面。消息的长度与频率上限挡住了单条与瞬时的极端值，却没有挡住累计：状态可以一直长，写入可以一直发生，一张卡就能让其他看板的写入排队。布局提交的回包又把全部看板的数据与状态带回来，拖动一次的成本随全部卡片增长。

## 决定

- 浏览器半边为每张卡建一个状态队列：同一个 250 毫秒窗口里的补丁按一层合并，最多每窗口提交一次；同一张卡同时只有一个请求在途，失败按 1、2、4、8 秒退避，连续失败超过五次停止自动重试。暂停、页面隐藏与卸载时立即提交。原生组件走同一个队列。
- 宿主核对两条额度：一张卡的状态最多 64KB，一块看板上全部卡片的状态合计最多 1MB。超出的写入回 413，不写进磁盘。
- 宿主核对两条频率：一张卡每秒最多 10 次状态写入，一块看板每秒最多 20 次。超出的回 429。限额只拒绝，不排队等待；宿主收到仍然同步写入（D5）。
- 卡片状态事件在对象合并时只带补丁 `patch`，整体替换时带整份 `state`；客户端按与宿主相同的一层合并规则并进页面。
- 布局提交成功时只回这次落定的盒子与修订号；修订号过期时回整份工作区。页面把前者与布局事件按同一条规则合并。
- 额度与频率的拒绝原因显示在卡片上，不静默丢弃。

## 后果

- `setState` 最多晚一个窗口（250 毫秒）写进磁盘；页面崩溃时最后一份可能丢失。组件状态本来就是界面状态，这个窗口是可接受的代价。
- 大状态组件会被额度挡住；需要持久化大块数据的组件应改用数据源与 `data`，或等 D5 的分表布局。
- 整块看板一次写入的代价没有消失，只是频率与总量被压住；卡片多到写整份文件变慢时，仍按 D5 的重审条件改分表。
- 状态事件里的补丁比整份状态小，在线页面合并的成本随改动而不是状态总量增长。

## 重审条件

- 出现需要高频持久化状态（逐帧绘制、大块编辑）的组件时，把状态移出看板文件、按卡分文件，并决定合并窗口与崩溃恢复。
- 额度挡住合法组件时，按组件或来源调整额度，并重新决定拒绝的可见形态。
- 出现按会话或按来源的信任分级时，额度与频率可以按来源分档（D6 的重审条件）。
