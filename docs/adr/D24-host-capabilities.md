# D24. 宿主能力：一条通用调用与能力注册表

## 背景

桥上的消息此前只有 `ready`、`setState`、`action`、`height`、`error`、`notify` 六种；读数据由宿主推给卡片，动作是单向的。每加一种需要参数、返回值、超时或取消的功能，就得在桥、路由与设置界面里各加一套形状。数据源与动作已经能由别的插件注册（D17），但一类新的 DSH 宿主服务（例如账号余额）仍然要在看板插件里写一遍专门的数据源与界面。

宿主有很多只读且已经由宿主自己授权的服务（`ctx.deepseekAccount` 的余额是其中之一）。把每一个都写成看板插件里的一条数据源，既把功能与看板核心绑在一起，也让第三方插件重复实现同样的桥。

## 决定

- 桥只保留一种调用：组件发 `call`（`requestId`、`capability`、`args`）与 `cancel`，宿主回 `call-result` 或 `call-error`。取消会中止宿主侧的在途调用；超时由宿主与运行时两头兜底。桥不再为每一种功能加消息类型（D3、D18）。
- 组件 manifest 增加 `capabilities`：一组能力名，需要时写成 `提供方:名字`。声明是允许调用的白名单；宿主不认识的能力名在调用时可见地拒绝。
- 宿主维护一张能力注册表。插件经 `widgetBoard` 服务注册 `CapabilityRegistration`：名字、给人和模型看的标题与说明、输入与输出的 JSON Schema、可选的权限、可选的凭据声明、带 `AbortSignal` 的 `call`。注册随组件目录的生命周期把手释放（D12、D17）。
- 宿主只做解析、鉴权、校验、超时与回传：调用前按输入 schema 校验参数，调用后按输出 schema 校验结果；声明了权限的能力要有一份绑在这张卡当前组件版本上的授权（D6）；失败原因原样回给组件。
- 数据源、动作与能力各自保留：数据源是带刷新策略的读，动作是单向的写，能力是带参数、返回值与取消的调用。设置弹窗把它们按同一份读模型展示；能力声明的凭据与组件自己声明的合在一起显示（D22）。
- DSH 账号余额是一个内置能力 `dsh.account.balance`：一个 `dsh-account` 提供方用 `ctx.deepseekAccount.getBalance` 包装，不声明权限（登录本身就是授权），返回充值钱包与赠送钱包。余额卡只声明这个能力并调 `widget.call`；看板核心不认识 DSH。
- 不做任意的 `ctx` 代理，也不把宿主的 `/api` 路由开给组件：能力必须显式注册，schema 与权限由提供方声明，token 与密钥不进入返回值。

## 后果

- 加一类新的宿主服务只需要一个提供方注册与一个组件声明；桥、路由与设置界面不再逐功能改动。提供方仍是代码，但它是能力的所有者。
- 桥多了一套请求/响应/取消的形状；`contracts` 里多一种服务注册项与一种授权类型，宿主多一条 `/instance/<id>/call` 路由，客户端多一次 `call` 的实现。这些只加一次。
- 调用时限 15 秒、消息上限 64 KB；结果过大或超时给可见的错误，不把卡片留在等待里。
- 输入与输出 schema 不合格、能力没装、没声明、没授权、提供方抛错都回可显示的原因；组件据此把失败画出来（D11）。
- 组件的 manifest 多一项；内置组件与插件组件用同一种声明（D7）。

## 重审条件

- 出现需要流式返回、双向订阅或长连接的能力时，重新决定桥上的调用形状与背压。
- 同一个能力需要按卡片保存不同的参数或凭据、或按用户区分时，重新决定能力注册的参数与存储。
- agent 也要直接调用宿主能力时，决定扩工具还是另加一条工具；权限与 schema 仍按能力注册表。
- 需要把宿主能力暴露给非 DSH 宿主时，重新决定服务发现与版本协商；不引入任意 `ctx` 代理。
