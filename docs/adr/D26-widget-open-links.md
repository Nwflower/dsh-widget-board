# D26. 组件请宿主打开链接

## 背景

组件文档的来源是不透明的，`sandbox="allow-scripts"` 也不带 popups 与 top-navigation（D3）。实测四种做法：组件里 `window.open` 与 `<a target="_blank">` 都不产生新页；给 iframe 加 `allow-popups` 能开，但那一个属性对所有组件生效，任何组件都能凭它把页面弹出去；点击之后经消息端口让父页面 `window.open`，用户激活跟着端口过来，新页正常打开。

卡片上列着要处理的 issue、仓库、链接，没有一样点得动，是这张看板最缺的东西。`links` 卡此前干脆写明「只展示，不做成可点」。

## 决定

- 桥上加一种消息 `open`，带一个地址；`window.widget.open(url)` 发它。父页面收到后在宿主页面里 `window.open(url, '_blank', 'noopener,noreferrer')`。
- 地址由 `isOpenableUrl` 判定：非空、不超过 2048 字符、能被 `new URL` 解析、协议是 `http:` 或 `https:`。判定在 `isWidgetMessage` 里做一次，两端的消息校验共用它。
- 不加 `allow-popups`，导航仍然一次都不给组件。组件拿到的能力是「请宿主开一个网页」，开的是宿主自己的新标签页，与宿主页面里点一个链接等价。
- 原生组件（D3 的原生级）在 `WidgetHandles` 上拿到同名方法，直接调同一段代码。
- 会话里的只读快照也允许跳转：它不需要写宿主，也不需要能力。

## 后果

- 跳转必须写在点击处理里。浏览器的用户激活有期限，隔着一次异步调用再开会被拦；组件作者得在点击的那一下直接调。
- 地址在父页面打开，所以组件的 CSP 不拦它；风险由协议白名单挡住，看板不判断地址指向谁。
- `links` 卡这类原本只展示的组件，可以改成可点的了。

## 重审条件

- 宿主提供自己的「打开链接」服务时，改由那项服务打开，交给宿主的侧栏浏览器或桌面应用。
