# D31. 提供方契约：两侧把手、作者域与执行上限

- **取代**：D12

## 背景

D12 定下三件事：两侧各发布一个带版本常量的 `widgetBoard` 服务、注册面是 `registerWidgetType` 加 `registerDataSource` 与 `registerAction`、版本对不上时可见地拒绝。它当时只有版本 2 的注册面，与提供方的约定只到「一次目录注册拿一个生命周期把手」这一层。之后三处变化各自落在别的方向里，D12 没有跟着改：

- D24 加了宿主能力，注册面多出 `registerCapability`，凭据、参数与结果 schema、超时与中止信号进了注册形状。
- D8 与 D30 引入带作者域的组件 id，市场条目按 `<作者域>.<名字>` 起名，本地组件继续用扁平 id。
- 组件的目录、数据源、动作、能力与市场都归同一个提供方，撤下时必须一次走完；旧入口一次注册一样东西，卸载时要由调用方逐项释放。

结果是一份提供方契约写成三处：版本协商在 D12，能力在 D24，作者域在 D8 与 D30，而「一个提供方在一侧只有一个把手」「入口怎么选」「配额与执行上限」没有地方写。升到版本 3 让这个缺口变成阻碍：新入口与旧入口同时存在，作者域的强制范围、功能声明与版本的关系、超时与并发口径都只能从代码读出来。

## 决定

### 服务与两个入口

- 宿主进程与浏览器页面各发布一个 cordis 服务 `widgetBoard`，各自报 `apiVersion`、`supportedApiVersions`、`features` 与 `supports(feature)`。新增方法或可选字段不升主版本，既有提供方照旧工作；移除旧方法或改变既有语义时升主版本，旧入口接受集合里列出的版本。
- 新入口 `registerProvider` 只接受最新的主版本，报身份与用途，返回一个把手；组件目录、数据源、动作、能力、市场与原生组件都挂在这个把手上。旧入口继续接受集合里的每个版本，供既有提供方使用。
- 版本不符时抛出并写明两侧的版本；未知的功能名在注册处抛出，`supports` 遇到未知名字同样抛出，不把它读成「不支持」。
- 弃用期按主版本算：一个方法标上弃用之后至少留到下一个主版本才移除，这期间旧入口照原样接受它；移除时调用处的错误写出替代它的方法与新位置。标弃用的时点、移除的时点与那一次的版本差异都记在 `service.ts` 的版本注释里。
- 版本常量留在运行时文件里，`./service` 只有类型。供提供方构造入参的纯值 SDK 放在 `./provider`：它校验名字、版本、功能名与每项注册必需的函数，返回冻结对象，不导入宿主实现。

### 一个提供方一个把手

- 同一侧、同一个提供方包名，同一时刻只有一个活动把手；新旧两个入口在同一个提供方上不能混用，混用时后到的那一次抛出并说明先释放什么。旧入口名下的注册全部释放之后，同一个提供方可以改用新入口。
- `dispose` 之后可以重新注册同一个提供方。撤下是提供方名的范围：目录、名下的注册、市场、这个提供方留下的授权与目录监视一起走，随后重读组件库。
- 新把手下方的子注册只写自己的名字与行为，`apiVersion` 与 `provider` 由把手注入。旧入口目录把手上的 `register` 收完整注册，并要求 `provider` 与把手相同。

### 功能与版本分开数

- `features` 是注册时对用途的声明，不改变这一侧提供什么；某一侧缺一项时按项降级，声明里写错一个名字则整次注册失败。
- `supports` 由这一侧自己回答，不替另一侧回答。首版四项是 `capabilityMetadata`、`eventData`、`marketProvider` 与 `pushData`：宿主侧四项都有，浏览器侧只有 `eventData` 与 `pushData`。
- 功能清单与版本集合各有一份来源，兼容表引用它们，不抄第二份。

### 作者域与旧 id

- 新把手挂的组件目录、市场来源与浏览器侧的原生组件都要求 id 写成 `<作者域>.<名字>`；本地来源与旧入口继续用扁平名字，带点的 id 在本地来源里读取即被拒绝。
- 已经装好的扁平 id 记录不改名，看板上的卡片按 id 解析。作者域只约束新目录，不触发既有记录迁移。
- 作者域扩展到浏览器侧的原生组件是本决定新增的一条：D8 与 D30 只把作者域用在市场条目与组件目录上。D30 的索引格式、分发与信任方向不变，D17 的来源次序与版本库方向不变。

### 执行上限与健康

- 数据读取与动作执行每次 15 秒，能力调用按注册声明的 1 到 25 秒（缺省 15 秒）；超时对调用方判失败并中止提供方。
- 每个提供方同时 8 个执行槽，槽在提供方的 promise 结束之后释放；槽占满时立即拒绝，不排队。
- 每个提供方最多 128 个组件（按去重后的 id 计）、64 个数据源、64 个动作、64 个能力，市场一个。
- 拒绝带原因码（超时、并发已满、调用方已取消），路由把超时与并发已满分别翻成 504 与 429。数据不合组件 schema 算提供方的一次失败，失败只记在读取路径上。
- 宿主按提供方记一份健康记录（声明过的功能、累计注册、失败、超时、现在是否可用、最近一次错误），随工作区快照交给页面，设置页列出这张表。可用性与计数分开：撤下之后可用为假，重新注册恢复可用，计数不清零。
- 卡片照自己的故障显示，一个提供方出错不影响别的提供方。

### 旧把手的生命周期

- 停用或卸载一个提供方时，它注册的组件、数据源、动作、能力与市场一起撤下，授权清掉，目录监视停下；卡片保留并画成不可用，提供方装回来即恢复。
- 原生组件撤下时，组件库里的记录还在，那张卡回退到沙箱组件；提供方整体停用或卸载时组件目录一起撤下，卡片画成不可用。

## 后果

- 服务面是公开契约：移除旧方法或改变既有语义才升主版本，新增方法与可选字段留在同一个主版本里；版本差异与旧入口的保留范围写进版本注释。
- 旧提供方不需要跟着迁移：旧入口继续接受它所属的版本，不设全局迁移期限。同一个提供方要改用新把手时，先释放旧入口的注册再启用新把手，两条路不能同时占用。
- 扁平 id 与带作者域的 id 长期并存，来源决定哪一种合法：带点的 id 只出现在带作者域的来源里，扁平的 id 也可能来自插件旧入口，读的人要从来源判断归属。
- 128/64/64/64 与 8 个执行槽是硬上限，超出时要由提供方自己拆分或分批，看板不替它排队。
- 健康计数按提供方累计、不清零，判断现在能不能用要看可用性那一位，计数只说明历史。
- 仓库里不另写一份完整契约文档：机制与数值读代码，方向读这一页，面向提供方的说法在 `docs/provider.md`。

## 重审条件

- 出现两个以上真实的提供方之后，按它们的实际需要重新审视服务面与把手的分组（D12 的重审条件由此承接）。
- 服务面升到下一个主版本时，重新决定旧入口保留几个版本、移除旧方法时错误里要写出什么。
- 需要按提供方分别给配额，或让提供方自己声明配额时，重新决定 128/64/64/64 与执行槽的固定值。
- 需要真正的作者身份验证时（D30 的重审条件），重新决定作者域来自声明还是来自验证。
- 需要把健康记录交给宿主自己的诊断界面时，重新决定这份快照的归属。
