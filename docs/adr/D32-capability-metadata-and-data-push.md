# D32. 能力元数据、按需读与数据推送

## 背景

D24 定下一条通用调用 `call`、一张能力注册表与 manifest 的 `capabilities` 白名单。握手时父页面只把当下能调的能力名交给组件，组件据此避开注定失败的调用。名字够用，但注册项上的标题、说明、参数与结果 schema、权限都没有到组件手里：一件能力该画成什么样、要不要先请人授权、参数有什么约束，作者只能自己写一遍。提供方晚装或被撤下之后，组件也看不出差别。

数据一侧只有读：宿主按刷新策略替卡片读一次，或者由人按下刷新。一张要跟着外部变化走的卡片——在跑的命令、正在被推送的会话、有人正在编辑的文档——只能靠定时轮询，而 D6 的定时链按看板整体算一轮，单张卡改不动自己的频率。

需要的材料都在，缺的是一处写下来的形状：能力注册项在宿主里，数据源的读函数在注册表里，握手里只有名字。

这一页补上三处缺口：能力的元数据、按需读的白名单与数据源的推送。D6 的数据源、授权与刷新方向，D24 的通用调用与注册表方向都不变。

## 决定

### 能力随握手给一份元数据

- `init` 携带 `capabilityMetadata`，按 manifest 的声明次序逐项给：`id`、`provider`、`title`、`description`、`input`、`output`、`permission`、`available`。
- 可用项从注册项取实值，字段与 `CapabilityRegistration` 同名；不可用项只留 `id` 与 `available: false`，其余字段没有。
- `provider` 只在能从声明的名字（`提供方:名字`）或全局唯一的注册解出来时给。解不出来时省略这一项，不用空串或占位名冒充提供方。
- 元数据只随 `init` 给一次。之后提供方撤下、名字重新解析这些事情不再发消息：一次调用失败回 `call-error`，组件据此把那一项标成不可用。
- `description` 在交给组件之前按语言各自截到 512 个 Unicode 码点：超出时留前 511 个码点再加一个省略号。按码点切，不按 UTF-16 单元切，emoji 的代理对不会被切开。截断之所以要有，是因为一整条 `init` 受 `PARENT_MESSAGE_LIMIT` 约束，一项说明够长就能把预算吃光；截断不新增消息。
- 截断只发生在交给组件的元数据上，注册项里的说明保持完整：设置弹窗读注册项，看的是全文。
- 形状由 `isParentMessage` 按整项判定：不带这个字段的旧 `init` 照旧合法；带了这个字段而其中一项不合形状，整条 `init` 当作没有发过。

### 兼容字段

- `widget.capabilities` 保持字符串数组：manifest 声明过、当下解析得到的 id。旧组件不改一行继续工作。
- 新增 `widget.capabilityMetadata`：与 `init` 里那一份同形的数组。两个公开字段都由运行时从元数据投影出来，旧字段的语义与内容不变。
- `init` 里旧的 `capabilities` 字段留着，带元数据时它等于其中 `available` 为真的那些 id，两份不会说两套话。
- 快照里的 `WidgetSummary.capabilities` 是 manifest 声明的白名单，与当下能不能调无关；`availableCapabilities` 是它的可用子集；`capabilityMetadata` 按 manifest 的声明次序带着每一项，含 `available: false` 的那些。三份由同一份能力面投影出来：`capabilities` 是元数据的 id 序列，`availableCapabilities` 是其中 `available` 为真的 id 序列，宿主同时填充；客户端只经工作区快照就能取到每一项的标题、说明与 schema，不必先发一次调用。判断一项能力现在能不能调，看 `availableCapabilities` 或元数据里的 `available`。
- 原生组件的参数里有同名的 `capabilities`、`capabilityMetadata`，并补一个 `lang`。这三项可选：省略表示这一侧没有投影能力面，组件按空能力面处理。原生与沙箱两种写法仍然同形。

### 按需读的白名单与权限叠加

- manifest 增加 `sources`：额外的数据源名，白名单。`source` 仍是默认源，并且总可读。
- 按需读走能力 `widget-board:data.read`：组件给出一个源名，宿主先判它在这份 manifest 的源集合里，再转给数据源的 `read`。不在白名单里的源直接拒绝，原因可见地回给组件。
- 能读一个源要同时过两道：manifest 的 `source` 或 `sources` 里有它，且没有越过提供方注册项声明的 `permission`。注册项声明了权限时还要一份绑在这张卡的组件版本上的授权，与 D6 的读路径共用同一份授权表与同一条只由人给授权的规则。
- 白名单是 manifest 的内容：改它就让内容哈希变，已有授权随之失效。

### 数据推送

- `DataSourceRegistration` 增加可选的 `subscribe(instance, emit)`，读一次的 `read` 照旧注册，两者的实现互不要求。
- `subscribe` 返回同步的退订函数。宿主在卡片离开视口、盒子不可见、提供方撤下时直接调用它；实现要在里面停掉自己的计时器与在途请求，不留回调。
- `emit` 推上来的数据按组件 manifest 的 `data` schema 校验，写入走与读取同一条路径与同一套修订号规则（D5、D23）。
- 订阅只在有人看着、且卡片可见时运行。同一张卡上订阅与定时刷新不会同时跑：声明了 `subscribe` 的源按订阅走，没声明的按 manifest 的刷新策略走。
- 订阅身份包含卡片 props 的稳定 JSON 表示，失败去重键同样带上它。`subscribe` 拿到的是订阅成立那一刻的卡片面，props 变了而订阅还在时实现一直读旧值；所以 props 一变，宿主先同步调用旧的退订函数，再用最新的卡片面重订。表示与键序无关：内容相同、只有键序不同的重同步不退订也不重建。
- 推送归数据源：动作仍然单向、没有返回值（D6）。

### 动作仍单向

- 组件发动作、发能力调用，宿主回应调用结果；没有第二条从组件到数据源或动作的双向通道。
- 需要宿主主动把东西交给组件时走数据：卡片的数据、能力返回值、看板栏上的通知。

### 排除项

- 不做流式能力：`call` 一次给一份结果，分片返回要重新决定桥上的形状。
- 不做组件自己发起的订阅：订阅由宿主按观众与可见性管理，组件不持有数据源。
- 不新增父页面消息类型：元数据随 `init` 走，之后的变化由调用失败表达。
- 不改市场、费用与作者域：D30 的分发与信任方向不变；D31 的把手与执行上限不变。
- 不做按来源或按作者的信任分级：授权仍然只由人给出。

## 后果

- 组件在调用之前就能把能力画成说明与权限提示，不再照文档自己写一遍；提供方撤下之后，组件看得出哪一项不可用。
- 探路的调用少一次：先读 `available` 再决定，省掉一次注定失败的请求和一轮授权询问。
- 一个源要多声明一次：默认源写在 `source`，额外源还要列进 `sources`；漏写就是读不到，错误在读取时可见。
- 数据源多一种形态：读一次与持续推两种，后者要自己管退订与在途请求，宿主不替它停计时器。
- 改一张卡的 props 会让它的订阅退掉重订一次：提供方每次 `subscribe` 都要自己推一次初值，初值只在订阅里推的实现不会漏掉这一步。
- 注册项里写很长的说明不再原样进 `init`：组件看到的是截到 512 个码点的那一段，全文留在设置弹窗里。
- 元数据只在握手时给一次，提供方在会话中途换实现时组件看到的是旧的那一份，直到那张卡重新加载。
- 能力元数据、白名单与订阅都是公开契约：删字段或改语义要按 D31 的版本规则升主版本。

## 重审条件

- 需要流式返回、分片结果，或订阅要由组件自己发起时，重新决定桥上的形状与背压（D24 的重审条件由此承接）。
- 提供方在会话中途换实现、而组件必须看到新元数据时，重新决定要不要再发一条消息，以及那条消息要不要新类型。
- 一个组件的源多到白名单难读时，重新决定 `sources` 的形状与上限。
- 推送量让 D23 的写入合并不够用时，重新决定节流、丢弃与合并的规则。
- 同一个能力名由多个提供方注册、组件要按环境挑一个时，重新决定声明里点名提供方的写法。
