# D4. 断点与尺寸族

## 背景

同一个组件会出现在宽度差别很大的位置：中栏看板（宽度随侧栏收起、右侧栏打开而变）、会话正文、右侧栏、展开浮层、独立窗口，屏幕从窄窗口到超宽屏都有。组件作者无法为任意尺寸设计，测试也无法覆盖任意尺寸。要让「每种显示都测过」成立，组件可能拿到的像素尺寸必须落在有限个已知区间里。

## 决定

- 断点按看板容器的宽度判定，与窗口宽度无关。整页只有一个 `ResizeObserver` 观察看板容器。断点表写在 `contracts`，挑选原则是一列的宽度大致保持在 100 到 150 像素：

  | 断点 | 容器宽度 | 列数 |
  |---|---|---|
  | xs | < 560 | 2 |
  | sm | 560–899 | 4 |
  | md | 900–1279 | 8 |
  | lg | 1280–1759 | 12 |
  | xl | ≥ 1760 | 16 |

- 行高与间距是 rem 令牌，宿主的字号设置让整张看板一起缩放。
- 组件声明它支持的尺寸族，缩放只吸附到声明过的尺寸族。网格族：`s` 2×2、`m` 4×2、`l` 4×4、`wide` 8×2、`xl` 8×4、`hero` 占满整行高 3 行。位置族：`expanded`（展开浮层）、`inline`（会话正文，宽度是正文栏，高度由组件上报、有上限）、`rail`（右侧栏）。
- 每个尺寸族的像素范围由 `model` 从断点表算出，只有这一份；尺寸矩阵、自检与编写指南都读它。
- 每块看板为每个断点各存一份布局。用户在某个断点上调整过，该断点标记为 `customized`；其余断点由 `model` 从最近一次编辑的断点推导：按阅读顺序（先 y 后 x）排序，放不下的组件按尺寸族降级（组件可以声明降级顺序，未声明按面积），首次适配装箱，再向上压实。推导是确定性的纯函数。
- 宿主放置新实例时同时算出它在每个断点上的位置。
- iframe 的视口就是卡片的内容盒，组件自己的 `@media`、`vw`、`vh` 天然是容器查询。运行时在根节点写 `data-size` 与 `--w-cols`、`--w-rows`，按宿主字号设定根字号。
- iframe 不换父节点：换父节点会让浏览器重新加载它。展开时卡片元素原地切到浮层层级，用 View Transitions 过渡；固定到右侧栏、内联到会话、独立窗口都新建 iframe，从宿主取回状态。
- 整页一个 `IntersectionObserver`：离开视口的卡片收到 `pause`，停掉动画；非当前看板的 iframe 卸载。
- 拖拽与缩放进行中，所有 iframe 设为 `pointer-events: none`。gridstack 只负责交互；断点变化时由 `model` 给出列数与布局，gridstack 的 `change` 事件转成一次提交。

## 后果

- 组件只需要为声明的几个尺寸族各写一套排版，并在每个尺寸族的两端各看一次。
- 用户不能把卡片缩放到尺寸族之外的任意大小。
- 推导出来的布局在用户看来可能不理想；用户在那个断点上调整一次，它就成为定制布局，不再被推导覆盖。
- 断点表与尺寸族表一旦发布就是组件的公开契约，改动它要重跑全部组件的矩阵。

## 重审条件

- 实际使用中某个断点上大量卡片被降级，说明断点表或尺寸族表需要重新划分。
