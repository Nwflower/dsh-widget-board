# D5. 宿主权威、存储与修订号

## 背景

看板的写入者不止浏览器：会话里的 agent 用工具放置组件、推送数据，其他插件经服务注册组件，多个浏览器窗口可能同时打开同一块看板，浏览器关掉之后数据源仍要刷新。任务看板插件采用宿主权威的账本，自己写原子替换、修订号与迁移；宿主现在提供了带结构校验、单写入链与变更事件的存储域。

## 决定

- 宿主是看板、实例与组件库记录的唯一权威。浏览器半边是视图：取一次快照，再跟随 SSE 增量更新。
- 持久化用 `ctx.storage.domain.open(spec)`，记录结构用 zod 声明。存储内容：

  ```
  Board     { id, title, order, layouts: Record<Breakpoint, Item[]>, customized: Record<Breakpoint, boolean>, revision }
  Instance  { id, boardId, type, typeHash?, family, props, data, state, source, createdBy }
  Library   { id, origin, source, currentHash, history[], approvals, forkedFrom? }
  ```

  格式版本写在域的声明里；读到无法接受的旧记录时明确报错并保留原文件，不静默清零。
- 存储域只有一个写入者：宿主服务。工具、路由与其他插件都调用同一个服务，业务规则只写在服务里。
- 界面不写宿主没有确认过的状态。拖拽与缩放的本地预览是唯一例外：松手时带修订号提交，修订号冲突时以宿主的答复为准重画。
- 宿主上只有一个刷新调度器。一个实例只在有客户端显示它、或它的刷新策略声明需要后台保持新鲜时才刷新；没有任何观众的看板不轮询。
- 推送通道是插件路由上的 SSE，带心跳；断线后重新取快照，按修订号补齐。

## 后果

- 每个界面动作都有一次宿主往返；本地预览只覆盖拖拽与缩放这类需要逐帧跟手的操作。
- 用自建 SSE，与任务看板同一条路径，不依赖需要代码生成的宿主类型化远程调用。
- 实例的 `data` 与 `state` 也在存储域里，数据量大的组件要在数据源一侧裁剪；单条记录的大小有上限，写入超限时拒绝并报告。

## 重审条件

- 宿主向第三方插件开放不需要代码生成的类型化远程调用与事件流时，改用宿主的通道。
- 存储域的单文件布局在看板很多时写入变慢，改用 `per-record` 布局。
