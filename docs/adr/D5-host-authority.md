# D5. 宿主权威、存储与修订号

## 背景

看板的写入者不止浏览器：会话里的 agent 用工具放置组件、推送数据，其他插件经服务注册组件与数据源，多个浏览器窗口可能同时打开同一块看板。卡片的状态又要跟着组件走：番茄钟在切走、重挂、页面重载之后都该接着计时。界面自己存状态会让两个窗口各说各话，所以权威只能在宿主这一侧。

## 决定

- 宿主是看板、实例与组件版本的唯一权威。浏览器半边是视图：取一次快照，再跟随事件把改动并进来（D18）。
- 看板与实例存 `$DSH_HOME/widget-board/board.json`：先写临时文件再改名，写到一半的内容不会留在磁盘上；格式版本写在文件里，读到不认识的版本时明确报错并保留原文件，不静默清零。

  ```
  Board     { version, id, title, revision, layoutRevision, instances[] }
  Instance  { id, widget, hash, source?, props, data, state, layout }
  ```

  一份看板是一个原子提交的整体：一次布局提交要一次落盘，所以不拆成两张表。
- 组件版本另存 `blobs/<hash>.json`（D17）：卡片文档与内联显示都按哈希取，重启之后仍在。
- 写入只有一个执行者，串行排队：后一次看得到前一次的结果，磁盘上不会出现两份互相覆盖的看板。每次写入同步落盘，没有延后写。
- 两个修订号。`revision` 每次写入加一；`layoutRevision` 只在卡片增删与布局提交时加一。页面带着读到的 `layoutRevision` 提交布局，过期时宿主回 409 与当前快照，页面按它重画（D16）。组件状态的写入不碰 `layoutRevision`，同一页面上的计时器因此不会让一次正在进行的拖动变成过期。
- 界面不写宿主没有确认过的状态。拖拽与缩放的本地预览是唯一例外：松手时提交，以宿主的答复为准。
- 推送通道是插件路由上的 SSE，带心跳；断线由浏览器重连，重连之后宿主先补一条「重取快照」，中间错过的改动因此补齐（D18）。
- 宿主上只有一个数据源注册表与一个刷新入口：数据由数据源读出来之后写进卡片，读失败不写进卡片并说明原因（D17）。

## 后果

- 每个界面动作都有一次宿主往返；本地预览只覆盖拖拽与缩放这类需要逐帧跟手的操作。
- 整块看板一次落盘，卡片很多时每次状态写入都要写整份文件；组件状态本来就是小改动，写入频率由组件自己决定（D18）。
- 用自建 SSE，与任务看板同一条路径，不依赖需要代码生成的宿主类型化远程调用。
- 实例的 `data` 与 `state` 都在同一份文件里，数据量大的组件要在数据源一侧裁剪；请求体上限之外的写入被拒绝并报告。

## 重审条件

- 宿主向第三方插件开放不需要代码生成的类型化远程调用与事件流时，改用宿主的通道。
- 一块看板上的卡片多到每次写入整份文件变得可见地慢，或需要按卡片并发写入时，改用宿主存储域的分表布局。
- 出现多块看板时，把文件拆成每块看板一份并在启动时按需读入。
